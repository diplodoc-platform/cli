# Markup regression fixtures

`markup-regressions.json` contains small, hand-authored documents and explicit
expected output, not snapshots generated by the implementation under test.
The Tracker, Forms, Wiki and Games names describe representative documentation
patterns; these examples are synthesized, not copied from private documentation.
The YTsaurus example is a minimized, rewritten reproducer of the duplicate code
span observed during live translation. No internal source documents or model
credentials belong in this directory.

`markup-regressions.spec.ts` exercises the real provider, extractor, composition,
repair and persistent cache. Only the model response is replaced. Each faulty
response is tested both as a recoverable first attempt and as a persistent
failure. Persistent failures must preserve the source unit without caching it;
unaffected units must still translate. The literal-marker case guards against
overzealous removal of valid text and code.

Run from the repository root:

```sh
npm test -- src/commands/translate/providers/ai/markup-regressions.spec.ts
```

To add a regression, minimize the document, write the expected Markdown by hand,
and describe the model's mistake using `fault`. Keep actual formatting in
`source`, including list indentation, blank lines and YFM delimiters. A fixture
without `fault` is a preservation control. A fixture with `fault` also needs
`fallback`, the expected document after both attempts fail.

As a mutation check, temporarily bypass `markupStructureIssue`, run this file,
and restore the implementation immediately. All ten faulty-response assertions
must fail while the literal-marker control passes. This verifies that these
fixtures exercise the structural guard rather than only mocked responses.
