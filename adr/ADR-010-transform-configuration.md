# Transform configuration at the CLI parser boundary

The CLI builds an ordered list of Markdown callbacks through extension hooks. It also supplies plugin-only data such as dependency contents, asset contents, project entries and anchor resolvers. Markdown collection and linting have separate hook contracts.

The actual `Run.transform` parser boundary now uses the stable Transform `/configuration` and `/parser` entrypoints. `configureTransform` names the supported core options explicitly and selects the `none` feature preset. It adapts the existing hook callbacks with `defineLegacyPlugin`, retaining their order and binding the existing plugin data separately. This prevents default-registry insertion or reordering and preserves existing flat options for legacy callbacks. The generated positional IDs are local identities for anonymous callback entries; they are not public stable IDs across hook changes.

Typed extensions can use `definePlugin` to bind their own options and register the resulting `.plugin` through the existing CLI Plugins hook. Their configuration remains distinct from normalized shared path/logger/language context. Collection stays explicit: the same `.collect` function is registered through the existing Collects hook, whose CLI calling convention is unchanged. Parser configuration neither executes collection nor binds parser options to collection. Linting continues to receive the legacy callback list and flat options, avoiding a mixed legacy/new composition.

`tests/e2e/plugin-configuration.spec.ts` loads a real custom extension into the built CLI. It checks HTML and Markdown builds followed by MD → MD → HTML, include and asset preservation, collector identity and separate invocation, and setup options whose `path` key cannot replace document context. The existing native13/native15 six-extension matrix and ordinary CLI option tests retain the legacy output contract. Unit coverage compares actual legacy/new parser output, callback ordering and data identities; collection must not run during parser installation or rendering.

This migration does not expose a new CLI YAML schema, change the existing hooks, upgrade the independently owned markdown-it13 parser, or promise upstream services. Acceptance uses an exact installed Transform candidate with reviewed compatible companion artifacts. Registry version updates belong to the coordinated release, not local tarball paths in committed package metadata.
